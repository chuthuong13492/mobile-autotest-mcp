# ADR-0001: MCP SDK, protocol revision and transport

- **Status:** Accepted (planning). **Update 2026-10-23 (DISC-001):** interoperability with Claude Code 2.1.169 is verified ([RL-029](../research-log.md#rl-029--sdk-v2-supports-both-protocol-eras-over-stdio), [RL-030](../research-log.md#rl-030--claude-code-21169-interoperability)), and OQ-02 is closed.
  - **Update 2026-10-23 (MCP-001):** the server is built on `@modelcontextprotocol/server` 2.3.1 over stdio, with no HTTP transport. SDK v2 validates tool input itself and reports failures as unstructured text, so each tool is registered with a *pass-through* Standard Schema. It advertises the contract's JSON Schema (identical to the `packages/contracts/schemas` snapshots) but leaves validation to the shared contract boundary (`bindUseCases`), which returns the documented `E_VALIDATION` tool error with JSON-pointer issues. Tools are registered in catalog order, so `tools/list` is deterministic.
- **Date:** 2026-10-22
- **Deciders:** Principal Architect, MCP Engineer
- **Supersedes / Superseded by:** —

## Context

The server must speak MCP to Claude Code first (NFR-010) and keep the door open to other clients.

The current specification is 2026-07-28 ([RL-001](../research-log.md#rl-001--current-mcp-specification-revision)). It is stateless, requires `server/discover`, uses server-minted handles, puts Tasks in an extension, and uses MRTR elicitation.

The official TypeScript SDK v2 (`@modelcontextprotocol/server` 2.3.1, Node ≥20, Zod v4, `./stdio` export) implements that revision. SDK v1 stops at 2025-11-25 and only receives fixes ([RL-005](../research-log.md#rl-005--mcp-typescript-sdk-v2)). I have not verified whether an SDK v2 server interoperates with Claude Code's client ([RL-006](../research-log.md#rl-006--sdk-v2-compatibility-with-older-protocol-clients)). Claude Code documents 2026-07-28 behavior for elicitation ([RL-007](../research-log.md#rl-007--claude-code-mcp-behaviour-relevant-to-this-design)).

Node.js 26 is "Current" today (2026-10-22) and is scheduled for Active LTS on 2026-10-28. Node 24's maintenance start date (2026-10-20) has passed ([RL-011](../research-log.md#rl-011--nodejs-release-status)).

## Decision

1. Use the **official MCP TypeScript SDK v2**: `@modelcontextprotocol/server` with its stdio transport (`@modelcontextprotocol/server/stdio`). The `@modelcontextprotocol/node` adapter is added only if a Node HTTP transport is introduced later. Pin exact versions in the lockfile.
2. Target MCP revision **2026-07-28**. Implement the required `server/discover` through the SDK. The server stores no per-connection state: every stateful interaction uses explicit handles (`runId`, `planId`, `approvalRequestId`, `cursor`), as the specification recommends.
3. **Transport:** v1.0 uses **stdio only**. The server writes logs to stderr and never to stdout. Streamable HTTP is an extension point. It may not ship until SR-017 is implemented (OAuth 2.1 resource server, RFC 9728 metadata, RFC 8707 audience binding).
4. **Runtime:** Node.js **26** is the primary target from its Active LTS date (scheduled 2026-10-28). Node.js **24** is the compatibility target, and CI runs a matrix on both. Before 2026-10-28, development may use either line. Node 26 must not be described as LTS before that date.
5. **Fallback:** if DISC-001 shows that the pinned Claude Code client cannot interoperate with an SDK v2 stdio server, the tool layer stays SDK-agnostic. `apps/mcp-server` adapts the contracts to SDK v1 (`@modelcontextprotocol/sdk`) as a temporary transport, and this ADR is superseded accordingly. The domain packages must not import any SDK.

## Alternatives considered

| Option | Why not chosen |
|---|---|
| SDK v1 (`@modelcontextprotocol/sdk`) | It is in maintenance only and does not implement 2026-07-28. It remains the fallback. |
| A custom JSON-RPC implementation | Duplicates protocol work and adds conformance risk. |
| Streamable HTTP from day one | Requires an authorization server and a larger attack surface. Not needed for a local-first product. |
| Python SDK | Conflicts with the TypeScript stack constraint. |

### Phase 0 outcome (2026-10-23)

- The SDK v2 stdio server serves both protocol eras. Claude Code 2.1.169 connects with the **legacy `initialize` handshake at `2025-11-25`**.
- In practice, the server must therefore support:
  - the legacy era: server-initiated `elicitation/create`, with no `server/discover`-first negotiation
  - the 2026-07-28 era: `server/discover` and MRTR `input_required`
- The SDK handles both. Tool handlers that elicit must implement both paths, as `spikes/disc-001/server.mjs` demonstrates.
- The fallback in step 5 is **not needed**.
- Node 24.22.1 and 26.12.1 were both verified with the SDK. Node 26 is still not described as LTS before 2026-10-28.

## Consequences

- Only `apps/mcp-server` imports the SDK. Contracts remain plain Zod schemas, which can be converted to JSON Schema for any SDK.
- Stateless design suits durable runs: the client can reconnect at any time.
- Claude Code restarts the stdio server per session. Long work therefore runs in detached supervisors ([ADR-0007](ADR-0007.md)).

## Risks

- [RK-02](../risks-and-open-questions.md#rk-02): protocol and SDK churn. A new spec revision is only months old.
- [RK-12](../risks-and-open-questions.md#rk-12): client output limits.

## Verification and revisit triggers

- **Verification:**
  - DISC-001 spike: a v2 server with one tool returning `structuredContent`, plus an elicitation, exercised from the pinned Claude Code.
  - MCP-001 conformance test using the SDK client in-process.
- **Revisit when:** a new MCP revision is published, SDK v3 ships, Claude Code drops 2026-07-28, or a remote deployment is requested.
