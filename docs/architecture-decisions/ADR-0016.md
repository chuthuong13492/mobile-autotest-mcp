# ADR-0016: GitHub Enterprise Server is a first-class host

- **Status:** Accepted (planning). Implemented in 1.3.0; the live instance check is open (OQ-07).
- **Date:** 2026-10-28
- **Deciders:** repository owner
- **Supersedes / Superseded by:** supersedes the "GHES is out of scope" clause of the 2026-10-24 update to [ADR-0013](ADR-0013.md)

## Context

The repositories the tool is meant for live on a GitHub Enterprise Server (`ghe.coxautoinc.com`, version 3.21.6 per
[RL-036](../research-log.md#rl-036--ghes-instance-version-and-documented-capabilities)). The code already supported
any host that is listed in `github.hosts` with an `apiBaseUrl`: the REST client is host-agnostic, `gh auth token
--hostname <host>` is allowed, and publication scopes record the PR host. What blocked GHES was setup, doctor, the
Skill and a hard-coded `github.com` default.

## Decision

1. A GHES host is configured in the user config: `github.hosts: [{host, apiBaseUrl: https://<host>/api/v3}]`
   (`https` only). `autotest setup` adds it from a workspace's `origin` remote, or from `--github-host`.
2. `get_pr_context` without a host uses the workspace's configured host, else the host of its `origin` remote when
   that host is configured, else github.com. A host that is not configured is never contacted.
3. Credentials: the user's `gh` login for that host (`gh auth token --hostname <host>`), or `credentialRef: env:NAME`.
   The token is sent only to the configured `apiBaseUrl`.
4. Publication mechanisms are the same as on github.com: comment and commit status with a user token; check runs need
   an App or an Actions token and are reported `failed` honestly when refused.

## Alternatives considered

| Option | Why not chosen |
|---|---|
| Keep github.com only; GHE repositories use manual mode | The target repositories are all on GHE, so PR intake and publication would never be automatic for them. |
| A dedicated GHE client with its own settings | The REST client is already host-agnostic (base URL with `/api/v3`, same-base pagination); a second client would duplicate it. |
| Derive any host from a PR URL or remote without configuration | A PR URL or a remote in the repository would then decide where the token is sent (T-06); hosts must be configured by the user. |

## Consequences

- `autotest doctor` checks the `gh` login per configured host.
- Verified against a mock server under `/api/v3` (paging, errors, fallback). The live instance check stays open
  ([OQ-07](../risks-and-open-questions.md#oq-07)) until a read-only run against a real PR.

## Risks

- [RK-15](../risks-and-open-questions.md#rk-15): GHES feature gaps (API version header, rate limits, SSO for tokens).
- An organization may require SSO-authorized tokens: `gh auth login` then has to authorize SSO, or a token is referenced
  with `credentialRef: env:NAME`.

## Verification and revisit triggers

- **Verification:** mock-server tests under `/api/v3` (`apps/mcp-server/test/github.test.ts`, `packages/github`), setup
  and doctor tests with an enterprise host (`apps/cli/test/setup.test.ts`), and a read-only live check against a real
  PR ([OQ-07](../risks-and-open-questions.md#oq-07)).
- **Revisit when** the instance refuses the REST calls a user token needs, or the organization mandates a GitHub App.
