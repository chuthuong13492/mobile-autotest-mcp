# ADR-0010: Flutter host unit/widget tests as the first platform

- **Status:** Accepted (planning)
- **Date:** 2026-10-22
- **Deciders:** Principal Architect, Mobile QA Architect
- **Supersedes / Superseded by:** —

## Context

The first vertical slice has to prove the full workflow end to end: PR → plan → gate → authorization → execution → evidence → analysis → report. It should do that without simulator or device complexity, and without depending on private credentials.

Autotrader, the first reference target, is a Flutter app ([RL-A01](../research-log.md#b-autotrader-reference-repository-read-only-inspection-2026-10-22)) with 725 unit and widget test files. Its CI already runs them on Linux hosts ([RL-A06](../research-log.md#b-autotrader-reference-repository-read-only-inspection-2026-10-22)).

`flutter test` emits a documented JSON event protocol through `--file-reporter json:<path>` ([RL-014](../research-log.md#rl-014--flutter-flutter-test-reporting-options), [RL-015](../research-log.md#rl-015--dart-test-json-reporter-protocol)).

## Decision

1. The first adapter is `adapter-flutter`, and its scope is **unit and widget tests executed on the host** (`flutter test <paths>`, with no device).
2. Results come from the JSON reporter, written to a run-owned file. The adapter generates JUnit itself, because no maintained converter dependency exists ([RL-016](../research-log.md#rl-016--junit-conversion-package-for-flutter)).
3. **Demo target.** The v0.1 demo uses a **synthetic, public Flutter fixture app** (E2E-001). It has deterministic passing, failing, erroring and skipped tests, plus a controlled flaky test. The flaky test is seeded by an environment variable or a run-owned counter file, so it fails on the first attempt and passes on the retry. The fixture has no private dependencies.
4. **Autotrader.** Autotrader is an **additional, credential-gated acceptance** target (E2E-003). It runs only where Artifactory and GHE credentials exist. It is never a prerequisite for v0.1 or for passing CI on the AutoTest repository itself.
5. **Toolchain resolution.** The Flutter SDK is resolved in this order:
   1. explicit user configuration
   2. FVM (`.fvmrc`, `.fvm/`) when present
   3. `flutter` found on the policy allowlist

   The adapter reports conflicts between these sources (FR-007) and never switches SDK versions silently.
6. **Deferred to v1.1:** Flutter `integration_test` on simulators and emulators (FL-006), and the Autotrader Appium/LambdaTest suite (APM-002, reference only).

## Alternatives considered

| Option | Why not chosen |
|---|---|
| Native Android first | Gradle unit tests run on the host too, but the first reference target is Flutter. |
| Appium E2E first | Requires devices, the most infrastructure, and credentials. It also has the highest flakiness. |
| React Native first | No reference target is available. |

## Consequences

- v0.1 runs on Linux CI and on Mac with no macOS-only dependency.
- Device features (`list_devices`, `manage_simulator`) exist in the contracts from v0.1. Until v1.1 they return `E_CAPABILITY_UNAVAILABLE` for device actions; `list_devices` still enumerates them where the tools are present.

## Risks

- The JSON protocol may differ between Flutter versions. DISC-006 captures a corpus from 3.38.x ([RK-07](../risks-and-open-questions.md#rk-07)).
