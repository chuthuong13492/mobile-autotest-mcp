# ADR-0006: Approval sources, assurance levels, and separate execution authorization

- **Status:** Accepted (planning).
  - **Update 2026-10-23 (DISC-002):** a Claude Code `Elicitation` hook was shown to auto-accept with no human ([RL-031](../research-log.md#rl-031--an-elicitation-hook-can-approve-without-a-human-empirical)). The AL1 classification is confirmed, and OQ-04 is closed.
  - **DISC-003** found that local AL3 needs organization-level signing or FIDO hardware ([RL-035](../research-log.md#rl-035--al3-approval-feasibility-on-macos)). [OQ-13](../risks-and-open-questions.md#oq-13) remains open as an organization decision.
  - **Update 2026-10-23 (AUTH-001 – AUTH-003):** implemented in `packages/storage/src/approvals.ts`, `packages/policy/src/approvals.ts` and `packages/policy/src/authorize.ts`. Details settled in implementation:
    - **Scope digests** are SHA-256 over the canonical `{ kind, params }`. For `plan_execution` the params are the plan hash, the environment and a digest of the sorted, de-duplicated TestTarget set.
    - **Effective assurance is capped by source.** Elicitation counts as AL1. CLI and pre-authorization approvals count as AL2. AL3 counts only when an AL3 verifier confirms the record. Until OQ-13 and CI-003 settle, the default verifier confirms nothing, so AL3 claims count as AL2 (fail closed).
    - **The pre-authorization file** is `~/.autotest/preauth.yaml` (`version: 1`, `entries[]` with `id`, `scope: github_publish`, `environment`, `match: { host, owner, name, mechanisms[] }`, `expiresAt`). Only `github_publish` can be pre-authorized; an invalid file pre-authorizes nothing.

## Context

Some operations need a human decision:

- a `needs_review` plan
- coverage exceptions
- destructive device actions (P2)
- external writes (P3)

The agent must not be able to grant these approvals itself (SR-007). There are three candidate sources:

1. **MCP elicitation.** Claude Code supports it. However, Claude Code also documents an `Elicitation` hook that answers dialogs automatically, and an SDK host can approve programmatically. The server therefore cannot tell a human answer from an automated one ([RL-007](../research-log.md#rl-007--claude-code-mcp-behaviour-relevant-to-this-design), [RL-008](../research-log.md#rl-008--elicitation-is-not-proof-of-a-human-derived-finding)).
2. **A local CLI.**
3. **A pre-authorization policy file** stored outside the target repo.

On a single-user Mac, the agent's shell runs as the same OS user as the human (A-01). Any file-based or CLI-based mechanism is therefore *agent-resistant* rather than *agent-proof*, unless the agent's tools are restricted or OS user-presence is required.

Coverage evaluation and approval are separate from **execution authorization**. That is the per-run decision about whether this exact plan may run now, on these targets, in this environment.

## Decision

### 1. Assurance levels

| Level | Meaning | Sources |
|---|---|---|
| **AL1 — client-attested** | The MCP client reports a user action. It can be automated by hooks or hosts. | MCP elicitation (`accept`) |
| **AL2 — local out-of-band, interactive** | A human acts outside the agent's tool channel. This resists an agent but does not prove a human acted if the agent has an unrestricted shell. | `autotest approve` CLI with a TTY challenge; a pre-authorization policy file owned by the user, outside the repo |
| **AL3 — strong** | OS-level user presence, or an organization-controlled human review that the agent cannot forge. | A local approval record signed by a key whose OS access control requires user presence (candidate: macOS Keychain with Touch ID or password, evaluated in DISC-003); in CI, a GitHub PR review approval or a protected-environment reviewer, verified through the API by the CI job |

### Phase 0 findings on AL3 (2026-10-23)

> **Update 2026-10-24.** OQ-13 is closed as an accepted residual: no AL3 mechanism is implemented, CI (the other AL3 source) is out of scope, and the default verifier `NO_AL3` stays. Local approvals are at most AL2.

**Local AL3 candidates:**

| | Candidate | Requirements |
|---|---|---|
| (a) | Secure Enclave key with `.userPresence` | A helper signed with Developer ID and a provisioning profile granting `keychain-access-groups`. Unsigned or ad-hoc builds fail with `-34018` or are killed by the OS. |
| (b) | FIDO2 security key via OpenSSH `-sk` keys and `ssh-keygen -Y sign` | Hardware keys issued to approvers |

Until the organization chooses, local approvals top out at AL2, and scopes that require AL3 can only be approved through CI.

**CI AL3 rules** (specified, for implementation in CI-003). A PR review counts only if:

- its state is `APPROVED`
- the reviewer is a member of the configured reviewer team, and is neither the PR author nor a bot
- it was submitted after the commit that last changed the plan file
- its body contains the line `autotest-approve <planHash>`, matching the current hash exactly

Verification runs through the API in the CI job, using a read-only token.

### 2. Minimum assurance by action

The defaults below are policy-configurable **upward** only. Lowering a level below these defaults requires `allowWeakApprovals: true` in the user-owned config, and that setting is recorded in every report.

| Action | Local default | CI default |
|---|---|---|
| Execute a `needs_review` plan | AL2 | AL3 (org review) |
| Coverage exception | AL2 | AL3 |
| P2 device action on a non-owned or destructive target | AL2 | Not allowed in CI v1.0 |
| P2 action on a run-owned simulator/emulator (create, boot, shutdown, erase-owned) | none (P1-equivalent) | none |
| P3 GitHub publication | AL2, or pre-authorization with a matching scope | Pre-authorization from CI-level configuration (not repository content), or AL3 |
| A `fail` gate decision | Can never be approved; the plan must change | Same |

AL1 elicitation is still offered as the **first-contact UX**: the user sees the request in Claude Code. Under default policy, though, an AL1 response alone is **insufficient** for every row above. The elicitation dialog tells the user the exact `autotest approve` command to run. Policy may allow AL1 only for explicitly listed low-risk scopes.

### 3. Approval record

Every approval record must contain the following fields:

| Field | Content |
|---|---|
| `approvalId` | Identifier of the record |
| `scope.kind` | One of `plan_execution`, `coverage_exception`, `device_action`, `github_publish` |
| `scope.digest` | SHA-256 over the canonical scope object: `planHash` + environment + target-set digest, or the action parameters |
| `planHash` | When applicable |
| `environment` | `local:<hostId>` or `ci:<provider>:<repo>` |
| `policyVersion` | The policy version in effect |
| `source` | `elicitation`, `cli` or `preauth` |
| `assuranceLevel` | AL1, AL2 or AL3 |
| `approver` | OS username and, where available, a verified GitHub login |
| `createdAt` | Creation time |
| `expiresAt` | Expiry time |
| `maxUses` / `uses` | Use limit and current count |
| `state` | See below |
| `signature` | For AL3 |

**States:** `pending → approved | denied`; `approved → expired | revoked | consumed | superseded`. Only `approved` with `uses < maxUses` and `now < expiresAt` is usable.

**Default expiry and reuse:**

| Scope | Expiry | maxUses |
|---|---|---|
| `plan_execution` | 24 h | 3 (the initial run plus retries of the *same* plan hash and target set) |
| `device_action` | 1 h | 1 |
| `github_publish` | 1 h | 1 per `(repo, pr, headSha, reportHash, mechanism)` |
| `coverage_exception` | ≤ 30 days; must be ≤ the exception's own expiry | — |

**Staleness:** an approval is stale and unusable when any of `planHash`, `scope.digest`, `environment` or `policyVersion` differs. A plan edit therefore always invalidates its approvals. Revocation (`autotest revoke`) takes effect immediately, including for runs still `queued`.

### 4. Execution authorization

`policy.authorizeExecution()` is a pure function. `execution` calls it twice: when a run is created and again at dispatch. It returns `ExecutionAuthorizationDecision { result: "authorized" | "denied", reasons[], inputsDigest }`. Every check below must pass:

1. The plan exists, its stored hash equals a recomputed hash, and the request's `planHash` matches.
2. A current `CoverageDecision` exists for the plan and requirement set, with the gate policy version in effect.
3. The decision is `pass`, or it is `needs_review` with a usable approval at the required assurance level. A `fail` decision always denies.
4. The repository and workspace are allowlisted. The requested targets ⊆ the plan's eligible targets. Devices and environment are allowlisted.
5. Every adapter-resolved command is allowed by the executable and argument policy (a dry-run resolution).
6. Prerequisites are satisfied (toolchain present, device available).
7. Nothing invalidates the request: no revocation, no superseding plan version, no cancellation, no policy denial.

Anything unknown or unresolved results in **deny**. Neither `exec` nor the adapters trust the authorization decision on its own: `exec` re-checks the executable, the arguments, the cwd and the environment for every spawn ([ADR-0014](ADR-0014.md)).

### 5. Defense in depth on the client

- `request_approval` and `publish_github_report` set `_meta["anthropic/requiresUserInteraction"]: true` so that Claude Code always prompts for them. This is advisory and is not relied upon.
- The setup guide recommends Claude Code permission rules that deny the agent the following: `Bash(autotest approve*)`, `Bash(autotest revoke*)`, and edits under `~/.autotest/**` (see [operations](../operations-and-troubleshooting.md#recommended-claude-code-permission-rules)).

## Alternatives considered

| Option | Why not chosen |
|---|---|
| Treat elicitation `accept` as human approval | Hooks and SDK hosts can automate it ([RL-008](../research-log.md#rl-008--elicitation-is-not-proof-of-a-human-derived-finding)). |
| Store approvals in the target repo | Content in the repo or PR is untrusted and could be forged by the PR author. |
| Fold authorization into the coverage gate | This would conflate coverage quality with permission to execute. The spec forbids it. |
| CI auto-approves `needs_review` | Explicitly forbidden. |

## Consequences

- Local `needs_review` flows require one terminal step, which adds friction on purpose.
- Approvals are portable across MCP sessions because they live in the user store.

## Risks

- [RK-01](../risks-and-open-questions.md#rk-01): an agent with an unrestricted shell can bypass AL2. Mitigated by permission rules, sandboxing, and AL3 where it is required. This is a documented residual risk.
