# ADR-0002: Modular monolith in a pnpm workspace

- **Status:** Accepted (planning)
- **Date:** 2026-10-22
- **Deciders:** Principal Architect
- **Supersedes / Superseded by:** —

## Context

The system covers many separate concerns: PR intake, inspection, planning, an independent gate, authorization, execution, devices, evidence, analysis, reporting, GitHub and storage. Its first deployment is a single local stdio process per developer session, plus a CI CLI. Splitting it into microservices now would add network, authentication and deployment overhead without an operational benefit. At the same time, boundaries must be strict: the gate must stay independent of planning, and adapters must not be able to execute arbitrary commands.

## Decision

1. Build a single pnpm workspace containing the packages listed in the canonical table in [architecture.md §Packages](../architecture.md#packages-and-dependency-rules), plus two deployable apps (`apps/mcp-server`, `apps/cli`) that share the same orchestration code.
2. Each package publishes a single `index.ts` entry point with explicit exports. Deep imports are forbidden ([ADR-0015](ADR-0015.md)).
3. Packages talk to each other through in-process calls and ports (TypeScript interfaces in `core`/`adapter-sdk`). The composition root in each app wires the implementations together.
4. **Extraction criteria.** A module may move into its own service only when a documented trigger occurs:

   | Module | Trigger |
   |---|---|
   | `execution` + `devices` → remote execution workers | Execution must happen on a remote Mac pool or on shared CI hosts that serve several clients; or the per-host concurrency limit becomes a bottleneck. |
   | `evidence` + `storage` → central artifact/run service | Several users or CI jobs need shared run history; retention needs object storage; or SQLite write contention is observed (RK-11). |
   | `github` → publication service | GitHub App credentials must be held centrally rather than on developer machines; or webhook-driven updates are needed. |

   The ports defined now (`RunStore`, `ArtifactStore`, `Publisher`, `ExecutionBackend`) are the seams for these extractions.

## Alternatives considered

| Option | Why not chosen |
|---|---|
| Microservices from the start | Adds authentication, transport and deployment complexity, and local-first use gets nothing for it. |
| A single package with folders | Boundaries cannot be enforced and circular dependencies creep in. |
| An Nx/Turborepo-centric build | Possible later. pnpm workspaces alone are enough, and fewer tools means less supply-chain surface. A task runner can be added under OPS-001 if build times call for it. |

## Consequences

- Adding a package is cheap. Dependency rules must be maintained ([ADR-0015](ADR-0015.md)).
- Everything runs in one process, so isolation from malicious test code relies on OS process boundaries ([ADR-0014](ADR-0014.md)), not on service boundaries.

## Risks

- [RK-09](../risks-and-open-questions.md#rk-09): scope creep across five platforms. Mitigated by the adapter capability model.

## Verification and revisit triggers

- **Verification:** OPS-003 dependency rules run in CI. Each package has its own test command.
- **Revisit when** any extraction trigger above occurs.
