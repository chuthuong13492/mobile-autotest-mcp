# ADR-0007: Asynchronous run model with a detached run supervisor

- **Status:** Accepted (planning).
  - **Update 2026-10-23 (EXE-001 – EXE-004):** the supervisor, the run-directory protocol and the queue are implemented in `packages/execution` and `packages/exec`. Details settled in implementation:
    - **Process identity** uses `ps -o lstart` (one-second resolution) plus the pgid. When the group leader is gone, a member is attributed to the run only if it started no earlier than the recorded leader; otherwise nothing is signalled.
    - **Dispatch re-authorization** is a supervisor hook. The EXE-003 baseline denies when policy cannot be loaded, the workspace is no longer allowlisted or executable, or any spec fails current policy in a dry run. The full `authorizeExecution` re-evaluation with digest comparison arrives in RUN-002.
    - **Attempts:** the supervisor runs one attempt; bounded retries (§9) arrive with RUN-003.
    - **Disk quota:** a breach cancels the run with the new cancel reason `resource_quota` (data model §Run lifecycle).
    - **Queue:** dispatch selection is a pure function over persisted runs, so several server instances decide consistently inside one SQLite transaction. It is work-conserving FIFO: a run blocked on its workspace or device does not block others. New `execution` settings: `maxRunsPerWorkspace` (default 1), `maxRunsPerDevice` (default 1), `queueCapacity` (default 20).

## Context

Mobile test runs take minutes or hours. Claude Code moves MCP calls that take longer than 2 minutes into the background, applies a 30-minute idle timeout to stdio, and starts a new stdio server process for each session ([RL-007](../research-log.md#rl-007--claude-code-mcp-behaviour-relevant-to-this-design)). MCP 2026-07-28 is stateless and recommends server-minted handles. Tasks are an opt-in extension, and no client is documented as supporting them yet ([RL-004](../research-log.md#rl-004--tasks-extension)). Runs must survive a client disconnect and a server restart (FR-029, NFR-005).

## Decision

1. **`run_tests` returns quickly.** It does the following, in order:
   1. validates the input
   2. computes the execution authorization
   3. persists a `Run` in state `queued`, durably committed in SQLite
   4. enqueues the run
   5. returns `{ runId, state: "queued", pollAfterMs }`

   `runId` is an opaque ULID-based handle with the format `run_<ulid>`.
2. **Run supervisor.** When a slot is free, `execution` spawns a **detached supervisor process** for each run. It is started from `packages/execution`'s own entrypoint with `node`; no shell is involved, and its argv is policy-checked. The supervisor:
   - owns the test child processes in its own process group
   - re-verifies authorization at dispatch ([ADR-0006](ADR-0006.md))
   - writes an append-only NDJSON event log and a heartbeat file in the run directory
   - writes a terminal record before it exits

   The MCP server is only an *observer*: it reads the files and updates SQLite.
3. **Process identity.** Each managed process is recorded as `{pid, pgid, startTime, executablePath, runId}`. `startTime` comes from the OS (`ps -o lstart`, or the platform equivalent behind an `ExecPort` abstraction). The child's environment also carries the marker `AUTOTEST_RUN_ID`. A signal is sent only when pid, start time and pgid all match the record. This prevents PID-reuse accidents.
4. **States.** The canonical state machine is in [data-model §Run lifecycle](../data-model-and-artifacts.md#run-lifecycle):

   `queued → preparing → running → collecting → analyzing → completed`

   with the transitional states `cancelling` and `cancel_pending`, and the terminal states `cancelled`, `timed_out` and `infra_error`.
5. **Cancellation.**
   1. Send SIGTERM to the process group.
   2. Wait for the grace period: default 10 s, configurable 1–120 s.
   3. Send SIGKILL to the group.
   4. Verify that no member of the group is still alive (by identity).
   5. If any member survives, for example a stuck simulator boot helper, set the state to `cancel_pending`, retry the verification on a back-off, and expose `cancelPendingSince` and `survivors[]`.

   `cancelled` is reported only after termination has been confirmed.
6. **Client disconnect** has no effect on runs. **Server shutdown** (stdio EOF or SIGTERM to the server) also does not stop supervisors. The run continues and finishes on its own.
7. **Restart reconciliation.** On startup, every non-terminal run is checked.

   | Condition | Action |
   |---|---|
   | Supervisor alive (identity match) and heartbeat fresh (< 3× the heartbeat interval) | Reattach |
   | Supervisor dead, terminal record present | Import the terminal record |
   | Supervisor dead, no terminal record | Kill surviving identity-matched children, collect partial evidence, then `infra_error` with reason `supervisor_lost` |
   | Identity cannot be verified | Never signal; `infra_error` with reason `orphan_unverified`, reported in `doctor` |

8. **Timeouts.** There are three levels: per test target (adapter-enforced where the runner supports it), per attempt, and per run (supervisor-enforced, wall clock). Expiry triggers the cancellation sequence and ends in the terminal state `timed_out`.
9. **Retry.** Retries follow the bounded retry policy (FR-028). Each attempt is a `RunAttempt`. Only `environment_failure` and `flaky`-eligible failures are retried by default.
10. **Duplicate requests.** `run_tests` accepts an optional `idempotencyKey`. A repeat with the same key and the same request digest within 24 h returns the existing `runId`. The same key with a different digest returns `E_IDEMPOTENCY_CONFLICT`.
11. **Tasks extension.** *(Update 2026-10-23: Claude Code 2.1.169 does not use Tasks ([RL-032](../research-log.md#rl-032--tasks-extension-in-claude-code)). MCP-003 stays conditional.)* An optional adapter (MCP-003) can wrap `run_tests` as an `io.modelcontextprotocol/tasks` task backed by the same run manager. It is enabled only when the client declares the extension and DISC-002 has verified support. It is not a dependency for v1.0.

## Alternatives considered

| Option | Why not chosen |
|---|---|
| A synchronous `run_tests` | It would hit client timeouts and backgrounding, and the work is lost when the session ends. |
| Children owned directly by the MCP server | The runs would die with the stdio server at session end. |
| A system daemon (launchd/systemd) | Needs installation privileges and adds lifecycle complexity. A per-run supervisor is enough. |
| Tasks as the primary mechanism | No client support has been verified. |

## Consequences

- The run directory becomes the source of truth for in-flight events. SQLite is the index ([ADR-0008](ADR-0008.md)).
- The supervisor code must be small and heavily tested, because it runs outside the server's lifecycle.

## Risks

- [RK-11](../risks-and-open-questions.md#rk-11): several server instances poll the same store. This is handled by per-run file locks and SQLite WAL with `busy_timeout`.

## Verification and revisit triggers

- **Verification:** RUN-004, RUN-006 and OPS-006 resilience tests:
  - kill -9 of the server mid-run
  - kill -9 of the supervisor
  - a child that ignores SIGTERM
  - a PID-reuse simulation
- **Revisit when** a client supports Tasks broadly, or remote execution workers are introduced ([ADR-0002](ADR-0002.md)).
