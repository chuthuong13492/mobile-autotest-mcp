# ADR-0003: Zod 4 schemas as the single source of contract truth

- **Status:** Accepted (planning)
- **Date:** 2026-10-22
- **Deciders:** Principal Architect, MCP Engineer
- **Supersedes / Superseded by:** —

## Context

Several things must agree on the same schemas:

- tool inputs and outputs
- persisted entities
- the plan-hash input
- reports
- CLI files

The SDK v2 examples use `zod/v4`, and the SDK accepts any Standard Schema library ([RL-005](../research-log.md#rl-005--mcp-typescript-sdk-v2)). Tool `inputSchema`/`outputSchema` must be valid JSON Schema 2020-12 ([RL-002](../research-log.md#rl-002--tool-annotations-are-untrusted-hints)). Claude Code also flattens root-level combinators and excludes tools whose schemas are invalid ([RL-007](../research-log.md#rl-007--claude-code-mcp-behaviour-relevant-to-this-design)).

## Decision

1. Every external or persisted shape is defined once in `packages/contracts` with **Zod 4**. TypeScript types are inferred from those schemas.
2. Tool input schemas are **objects at the root**, with no root-level `anyOf`/`oneOf`/`allOf`. Variants are expressed through a discriminator property (for example `source: "manual" | "github"`) with nested unions. This avoids Claude Code's flattening of root combinators.
3. JSON Schema 2020-12 is generated from the Zod definitions at build time and committed as a snapshot (`packages/contracts/schemas/*.json`). A CI check fails when the snapshot drifts without a matching version bump.
4. Every schema version is explicit: entities carry `schemaVersion`, and the plan carries `hashVersion` ([ADR-0005](ADR-0005.md)). Breaking changes require a migration in `storage` and a version bump.
5. Unknown properties are **rejected** (`strict`) on tool inputs and **stripped with a warning** on adapter-parsed external data.

## Alternatives considered

| Option | Why not chosen |
|---|---|
| Valibot / ArkType | Both are viable under Standard Schema, but Zod is what the SDK examples use and the requested default. |
| Hand-written JSON Schema plus generated types | Two sources of truth would drift apart. |
| TypeBox | Good for JSON Schema output, but less common with the MCP SDK. |

## Consequences

- One schema change propagates to tool definitions, storage validation and report schemas together.
- Strict input validation gives the model clear errors with JSON pointers (NFR-013).

## Risks

- Zod-to-JSON-Schema conversion edge cases (for example `.transform`). Transforms are forbidden in contract schemas; normalization happens in `planning`.

## Verification and revisit triggers

- **Verification:**
  - CON-007 snapshot test.
  - Contract tests that validate every documented example in [mcp-tool-contracts.md](../mcp-tool-contracts.md) against the schemas.
- **Revisit when** the SDK changes its schema mechanism.
