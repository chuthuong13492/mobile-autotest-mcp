# ADR-0013: GitHub App or Actions token for checks; scoped tokens for comments; status fallback

- **Status:** Accepted (planning). **Update 2026-10-24:** scope narrowed to **github.com**, authenticated through the user's `gh` CLI (`gh auth token`, run by `exec` as an allowlisted probe; the token stays in memory and is redacted). GHES is out of scope and DISC-005 was removed. With a `gh` user token, check runs usually return 403 (GitHub restricts them to Apps and Actions tokens); the client then reports `unavailable` and falls back to a commit status. **Update 2026-10-23 (DISC-005, partial):** the instance runs GHES **3.21.6**. The GHES 3.21 docs document the Checks API (write limited to GitHub Apps), `GITHUB_TOKEN` `checks: write`, ephemeral and JIT runners, and OIDC ([RL-036](../research-log.md#rl-036--ghes-instance-version-and-documented-capabilities)). Instance configuration is still unverified ([OQ-07](../risks-and-open-questions.md#oq-07)).

- **Deciders:** Security Engineer, DevSecOps Engineer

## Context

Publishing results to GitHub is optional and must be authorized (G-11, SR-009). The relevant platform facts, all from [RL-023](../research-log.md#rl-023--github-checks-api-write-access) – [RL-025](../research-log.md#rl-025--fine-grained-pat-permissions):

- **Check runs:** only GitHub Apps can create them. Inside Actions, `GITHUB_TOKEN` with `checks: write` can also create them, though this is not verified on GHES.
- **PR comments:** need Issues (write) or Pull requests (write).
- **Commit statuses:** need Commit statuses (write).
- **Reads:** fetching a PR needs Pull requests (read) or Contents (read).

## Decision

1. **Read-only by default.**
   - `get_pr_context` uses a read credential: a fine-grained PAT with Pull requests: read, or a GitHub App installation token with read permissions.
   - No write-capable credential is loaded unless publication is configured.
2. **Publication mechanisms, in order of preference.** Each is chosen by configuration and capability probing.

   | Mode | Primary | Fallback |
   |---|---|---|
   | CI on Actions | Check run using `GITHUB_TOKEN` with `permissions: { checks: write, pull-requests: write }` scoped to the job | Commit status |
   | Local or other CI | GitHub App installation token (checks: write, pull_requests: write) when the organization provides an App | Fine-grained PAT, comment-only (Pull requests: write), plus a commit status (Commit statuses: write) if granted |

3. **Every publication is P3.** It requires authorization per [ADR-0006](ADR-0006.md). The tool is single-use per scope digest `(repo, pr, headSha, reportHash, mechanism)`.
4. **Idempotency.**
   - Comments carry a hidden marker `<!-- autotest:pr=<n>;key=<stableKey> -->`. Publishing updates the existing marked comment authored by the same identity and never creates a duplicate.
   - Check runs use the `external_id` of `autotest:<planHash>:<runId>`, and the name `AutoTest / <planId>`.
5. **Limits.**
   - Annotations are posted in batches of ≤50 per request.
   - The summary is trimmed to stay within API limits, with a link to the full report artifact.
   - Rate limits are handled with exponential backoff that honours `retry-after` and `x-ratelimit-reset`. There are at most 5 retries.
   - Partial failure, for example a posted comment with a failed check, is reported per mechanism in the tool result and audited.
6. **Credentials never appear** in tool inputs, outputs, logs or reports. Credentials are resolved by reference from the secret source ([security-threat-model §GitHub credential matrix](../security-threat-model.md#github-credential-matrix)).

## Alternatives considered

| Option | Why not chosen |
|---|---|
| Classic PAT with `repo` scope | Over-privileged. |
| Comments only | Loses the structured check UX where it is available. |
| Always use the Checks API | Not possible without an App or Actions token. |

## Consequences

- Organizations without a GitHub App get comment and status publication only. The report states which mechanism was used.
