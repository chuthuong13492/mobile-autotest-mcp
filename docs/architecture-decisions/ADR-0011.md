# ADR-0011: Native runners first; Appium only where it adds value

- **Status:** Accepted (planning)
- **Date:** 2026-10-22
- **Deciders:** Mobile Automation Architect
- **Supersedes / Superseded by:** —

## Context

Each ecosystem already has a well-maintained runner:

| Ecosystem | Runner |
|---|---|
| Flutter | `flutter test` |
| iOS | `xcodebuild test` and XCTest |
| Android | Gradle unit and instrumented tests |
| React Native | Jest and React Native Testing Library; Detox or Maestro for E2E ([RL-020](../research-log.md#rl-020--react-native-testing-guidance)) |

Appium 3.8 is current ([RL-021](../research-log.md#rl-021--appium-current-version)). The Flutter integration driver on `main` declares a peer dependency on Appium 3 ([RL-022](../research-log.md#rl-022--appium-flutter-integration-driver-and-appium-3)). Autotrader's existing suite documents Appium 2 but installs it unpinned ([RL-A13](../research-log.md#b-autotrader-reference-repository-read-only-inspection-2026-10-22)).

## Decision

1. Use the ecosystem-native runner by default at every test level it supports.
2. Use the **Appium adapter** only when at least one of these holds:
   1. an existing Appium suite must be reused (for example Autotrader's scenarios)
   2. one black-box E2E flow must cover both platforms through a single driver
   3. system-level interaction is needed that the native framework cannot drive

   | Need | Default strategy | Appium when |
   |---|---|---|
   | Unit / widget / component tests | Native (flutter test, Jest, XCTest, JUnit) | Never |
   | Flutter in-app integration | `flutter test integration_test` | Reusing an Appium + appium_flutter_server suite |
   | Native UI tests | XCUITest / Espresso via the native runner | Reusing an existing suite, or one cross-platform script |
   | RN E2E | Detox or Maestro | Reusing an existing suite |

3. **Version pinning is mandatory.** The Appium adapter refuses to run unless the project configuration declares exact versions of the Appium server and each driver, and they match the installed ones. Global unpinned installs are reported as `prerequisite_mismatch`. Compatibility between Appium 3 and `appium-flutter-integration-driver` stays **Unverified** until [OQ-06](../risks-and-open-questions.md#oq-06) is closed.
4. Device farms (LambdaTest and others) are out of scope for v1.x. They may be added later as an execution backend behind the `ExecutionBackend` port.

## Alternatives considered

| Option | Why not chosen |
|---|---|
| Appium for everything | Slow and flaky, and a poor fit for unit and widget tests. |
| No Appium at all | Leaves existing suites such as Autotrader's unusable. |

## Consequences

- Appium arrives late (v1.2) and is optional.

## Risks

- [RK-14](../risks-and-open-questions.md#rk-14): Appium and driver incompatibilities.

- **Revisit when** a native framework drops support for a needed capability.
