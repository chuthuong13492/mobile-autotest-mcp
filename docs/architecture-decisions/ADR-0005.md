# ADR-0005: Independent, plan-hash-bound coverage gate

- **Status:** Accepted (planning).
  - **Update 2026-10-23 (COV-001 – COV-004):** the gate is implemented in `packages/coverage-gate` as pure functions with no `planning` import (dependency-cruiser enforced, tests included). Its configuration is a structural copy of the policy `coverageGate` section. Exception approvals are found by scope digest (plan hash + exception content) and verified through policy in the use case; the gate receives only the set of approved exception IDs.
    - `validate_test_coverage` re-evaluates the gate on every call, because exception approvals and expiry are inputs the three bindings do not capture.
    - The stored decision for identical bindings is reused when the result is identical. A changed result is recorded as a new decision, and the newest one is what authorization reads.
- **Date:** 2026-10-22
- **Deciders:** Principal Architect, Mobile QA Architect
- **Supersedes / Superseded by:** —

## Context

A plan generator should not approve its own output. Coverage must therefore be evaluated by separate code, using separate rules, over persisted data. Afterwards it must be impossible to execute a plan that differs from the one that was evaluated (FR-015, FR-017).

## Decision

1. **Separate package.** `packages/coverage-gate` depends only on `core` and `contracts`. It must **not** import `packages/planning`, and this is enforced by [ADR-0015](ADR-0015.md). It reads the persisted `RequirementSet` and the normalized `TestPlan` through a `core` port, and it ignores any generator-provided self-assessment fields: the plan schema has no such fields, and unknown fields are rejected.
2. **Rules and configuration** belong to the gate:
   - its own policy file section (`coverageGate`)
   - its own version (`gatePolicyVersion`, the SHA-256 of the canonical gate config)
   - mandatory blockers (GB-*), which cannot be disabled
   - configurable review triggers and thresholds (GR-*)

   The rules are defined in [test-planning-and-coverage.md §Gate rules](../test-planning-and-coverage.md#independent-coverage-gate).
3. **Decision binding.** A `CoverageDecision` records:

   | Field | Content |
   |---|---|
   | `planId` | The plan evaluated |
   | `planHash` | The hash of the plan version evaluated |
   | `requirementSetHash` | The hash of the requirement set evaluated |
   | `gatePolicyVersion` | The gate policy version used |
   | `decision` | `pass`, `fail` or `needs_review` |
   | `findings[]` | The rule findings |
   | `metrics` | The six metrics |
   | `evaluatedAt` | Evaluation timestamp |

   A decision is **current** only when all three bindings (`planHash`, `requirementSetHash`, `gatePolicyVersion`) equal the values in effect now. Otherwise it is **stale** and cannot be used.
4. **The hash** is SHA-256 over the RFC 8785 canonical JSON of the hash-covered plan fields, prefixed with `hashVersion`. It is specified in [data-model §Plan hash](../data-model-and-artifacts.md#plan-hash-specification).
5. **What the decision does and does not grant.**
   - `pass` does **not** authorize execution. It is one input to [ADR-0006](ADR-0006.md) authorization.
   - `fail` always blocks.
   - `needs_review` blocks unless a matching approval exists at the required assurance level.

## Alternatives considered

| Option | Why not chosen |
|---|---|
| Gate logic inside `planning` | A shared module could quietly reuse generator assumptions, so independence cannot be shown. |
| Decision bound only to `planId` | Edits under the same id would reuse the decision. |
| The agent self-reports coverage | Not trustworthy, and conflicts with the core principle. |

## Consequences

- Some normalization logic (ID formats, requirement lookup) is duplicated in `core` rather than shared from `planning`. That is acceptable: shared primitives live in `core`.
- A change in policy version invalidates decisions, so users must re-run the gate after a config change. This is intentional.

## Risks

- Rules that are too strict cause approval fatigue ([RK-10](../risks-and-open-questions.md#rk-10)). Thresholds are configurable within the limits the blockers allow.

## Verification and revisit triggers

- **Verification:**
  - dependency-cruiser rule `coverage-gate-not-planning` (OPS-003)
  - COV-004 staleness tests
  - SEC-003 tests: an edited plan cannot reuse the old decision
- **Revisit when** the gate needs semantic (LLM) review. That would be a new ADR, and its result would be advisory only.
